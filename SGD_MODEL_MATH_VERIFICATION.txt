5. IMPLEMENTATION BUGS — IDENTIFIED AND FIXED
================================================================================

5.1 BUG #1: SCALER REFIT IN update_model_partial_fit.py
────────────────────────────────────────────────────────

WHAT WAS WRONG:

  In the original update_model_partial_fit.py (lines 158-160 and 168-169),
  the script created a NEW StandardScaler, fitted it on the combined dataset,
  and saved it to disk — overwriting the original scaler:

    # ─── BUG ───
    scaler_new = StandardScaler()                        # NEW scaler
    X_combined_scaled = scaler_new.fit_transform(X_combined)  # FIT on all data
    ...
    joblib.dump(scaler_new, scaler_path)                 # OVERWROTE original

  This violated the "never refit" rule stated in Section 3.3 of the math
  document. The SGD model's weights (w = [170.41, 162.94, 210.75, 207.45],
  b = 146.95) were trained on features scaled with mu = [139.54, 114.79,
  142.50, 111.94] and sigma = [776.10, 808.21, 789.95, 802.52]. Replacing
  the scaler changes the feature space, making the existing weights invalid.

  Additionally, the R² evaluation used this new scaler, producing an
  artificially optimistic score because the fresh scaler perfectly matched
  the combined dataset's distribution.

WHAT IT WAS FIXED TO:

  The rewritten update_model_partial_fit.py now:
  (a) Uses the EXISTING scaler's transform() for ALL data (new, combined,
      and evaluation):
        X_new_scaled = scaler.transform(X_new)
        X_combined_scaled = scaler.transform(X_combined)
  (b) NEVER creates a new StandardScaler or calls fit_transform()
  (c) Does NOT save the scaler (it hasn't changed — no need to overwrite)
  (d) Reports scaled feature means to verify they are near 0 (confirming
      the new data matches the original distribution)

  Relevant code changes:
  - Line ~145: scaler.transform(X_new) instead of new scaler + fit_transform
  - Line ~185: scaler.transform(X_combined) instead of new scaler
  - Line ~205: joblib.dump(model, model_path) only — scaler NOT saved

  The scaler loaded in Step 1 is used for every transform and is never
  replaced. This matches the design described in Section 3.3 of the math
  document.


5.2 BUG #2: SIMULATED FEATURES INSTEAD OF REAL USER DATA
─────────────────────────────────────────────────────────

WHAT WAS WRONG:

  In the original update_model_partial_fit.py (lines 86-117), the script
  fabricated 4-month feature vectors from a single deviation value:

    # ─── BUG: Fabricated data ───
    deviation = entry['deviation']  # Single value (current month only)
    sample_features = [
        deviation * 0.7,  # Simulated — NOT REAL
        deviation * 0.8,  # Simulated — NOT REAL
        deviation * 0.9,  # Simulated — NOT REAL
        deviation * 1.0,  # Simulated — NOT REAL
    ]

  The math document's Section 10 describes using real historical deviations:
  "Compute deviations: dev_m = spend_m - budget_m for m = 1..4"

  But the implementation generated proportional estimates that encode no
  real behavioural signal. For example, if a user's current deviation was
  +500, the fabricated features were [350, 400, 450, 500] — a smooth rising
  sequence. The user's actual pattern might be [+400, -100, +400, -300] —
  a volatile, oscillating pattern. Feeding fabricated data to partial_fit()
  nudges the model's weights in random directions rather than toward a
  better fit on real patterns.

  The root cause was that the PHP orchestrator (update_model_month_end.php)
  only collected each user's current month deviation — not their full
  4-month deviation history.

WHAT IT WAS FIXED TO:

  Two files were rewritten:

  (A) update_model_month_end.php — Now queries each user's actual monthly
      spend AND budget for the last 5 months from the database, computes
      real deviations, and validates that the 5 months are contiguous:

      - Joins expenses with user_budgets to get actual spend vs budget
      - Groups by user and month, computing deviation per month
      - Filters for users with 5 contiguous months of data
      - Passes all 5 deviation values to the Python script:
          month1_deviation = dev_m-4  (feature 1, oldest)
          month2_deviation = dev_m-3  (feature 2)
          month3_deviation = dev_m-2  (feature 3)
          month4_deviation = dev_m-1  (feature 4)
          month5_deviation = dev_m    (target)

  (B) update_model_partial_fit.py — Now validates that all 5 deviation
      fields are present and numeric, rejecting incomplete entries:

      - Requires: month1_deviation, month2_deviation, month3_deviation,
        month4_deviation, month5_deviation
      - Validates each field is present and numeric
      - Reports rejected entries with reason
      - Logs feature statistics for the new data

  The updated pipeline now uses REAL deviation history:

    BEFORE (fabricated):
      Input: { "deviation": 500 }
      Features: [350, 400, 450, 500]  ← made up

    AFTER (real):
      Input: {
        "month1_deviation": 400,
        "month2_deviation": -100,
        "month3_deviation": 400,
        "month4_deviation": -300,
        "month5_deviation": 500
      }
      Features: [400, -100, 400, -300]  ← actual user history
      Target: 500

  This matches the design described in Sections 10 and 14 of the math
  document: the model receives the user's true behavioural pattern and
  learns from real spending outcomes.


5.3 VERIFICATION OF FIXES
─────────────────────────

  To verify the fixes are correct, the following properties should hold
  after a month-end update:

  (a) Scaler unchanged:
      - scaler.mean_ before update = scaler.mean_ after update
      - scaler.scale_ before update = scaler.scale_ after update
      - The scaler file on disk should be IDENTICAL (not replaced)

  (b) Real features used:
      - The update script output should show feature statistics for the
        new data (mean and std for each of the 4 deviation features)
      - These should be real deviation values (can be positive or negative),
        not proportional estimates of a single value
      - Rejected entries should be reported with specific reasons

  (c) R² is honest:
      - The R² score should be computed using the frozen scaler's transform,
        not a freshly-fitted scaler
      - The R² may be slightly lower than before (because the previous R²
        was artificially optimistic) — this is correct behaviour
