1. PROJECT OVERVIEW
================================================================================

SmartSpend is a personal finance management web application designed for
students in Lesotho. It automates expense tracking through SMS parsing of
bank transaction messages, provides spending predictions via machine learning,
and encourages sustained financial habits through gamification.

Core capabilities:
  - SMS-based transaction auto-import from 4 banks (FNB, Standard Lesotho
    Bank, M-Pesa, Nedbank)
  - Three-layer ML classification (hardcoded dictionary → learned memory →
    Naive Bayes TF-IDF)
  - Spending prediction using SGDRegressor trained on 500+ user records
  - Progressive prediction fallback for users with 0-3 months of data
  - Monthly budget setting with spending tracking
  - Savings goals with progress tracking
  - Gamification (XP, levels, 12 badges, 4 monthly challenges)
  - Real-time dashboard with category pie charts and transaction lists
  - Analytics with category breakdowns and weekly spending trends
  - Active learning loop: user corrections teach the AI over time

Two separate prediction pipelines exist:

Pipeline A — SGDRegressor (Monthly Spending Prediction):
  User adds expenses → BudgetContext calls get-prediction.php →
  PHP fetches last 4 months of spending → calls predict.php (PHP bridge) →
  predict.php spawns Python subprocess → run_prediction.py loads
  budget_model.pkl + scaler.pkl → predicts deviation from budget →
  Returns predicted_spend, predicted_deviation, confidence score

Pipeline B — Naive Bayes (SMS Classification):
  SMS received on phone → SMS Forwarder app → webhook to sms-ingest.php →
  PHP calls Flask /parse endpoint → classify_sms() runs 3-layer classifier →
  Returns category, confidence, needs_manual_category →
  PHP saves to expenses table + creates notification

4. PORT CONFIGURATION
================================================================================

Service             Port   Purpose
────────────────────────────────────────────────────────────
Vite Dev Server     5173   React frontend development server
Apache (PHP)        8080   REST API endpoints (62 PHP files)
Flask (SMS Class.)  5000   SMS classification + active learning
MySQL               3306   Database (smart_budget)

Development detection:
  - api.js checks if window.location.port is 5173/5174/5175
  - If dev mode: API_BASE → hostname:8080
  - If production: API_BASE → window.location.host (same origin)
  - ML_API_BASE is always http://localhost:5000

Vite proxy configuration (vite.config.js):
  - Proxies /smart_budget/backend → http://localhost:8080
  - This allows same-origin requests during development

8. BACKEND — SGDRegressor PREDICTION SYSTEM
================================================================================

Purpose: Predict end-of-month spending based on historical
budget-vs-actual patterns.

Algorithm: SGDRegressor (Stochastic Gradient Descent)
  - Loss function: squared_loss (linear regression via SGD)
  - Supports partial_fit() for incremental learning
  - Trained on 500+ user records
  - R² score: ~0.79-0.81 (stored in model_metrics.json)

Features (4 inputs):
  1. Month 1 spending deviation (month1_spend - budget)
  2. Month 2 spending deviation (month2_spend - budget)
  3. Month 3 spending deviation (month3_spend - budget)
  4. Month 4 spending deviation (month4_spend - budget)

Target: Month 5 spending deviation from budget

Preprocessing:
  - StandardScaler: normalizes 4 deviation features
  - Features scaled before prediction

Pipeline flow:
  1. User opens Dashboard/Analytics page
  2. BudgetContext.fetchPrediction(user_id) fires
  3. GET /api/get-prediction.php receives POST { user_id }
  4. PHP queries user_budgets for monthly_budget
  5. PHP queries expenses for last 4 months totals
     (excludes current month: DATE(date) < first-of-month)
  6. If < 4 months available, uses statistical fallback
  7. If 4+ months, PHP calls predict.php via cURL
     URL: http://{HTTP_HOST}/smart_budget/backend/ml/predict.php
     POST: { budget, month1_spend, month2_spend,
             month3_spend, month4_spend }
  8. predict.php writes JSON to temp file
  9. predict.php spawns Python subprocess:
     python.exe run_prediction.py {temp_file}
 10. run_prediction.py:
     a. Loads budget_model.pkl (SGDRegressor)
     b. Loads scaler.pkl (StandardScaler)
     c. Computes deviations = [m1-budget, m2-budget, m3-budget, m4-budget]
     d. Scales deviations via scaler.transform()
     e. Predicts: predicted_deviation = model.predict(scaled)
     f. Computes: predicted_spend = budget + predicted_deviation
     g. Ensures: predicted_spend >= 0
     h. Loads R² from model_metrics.json (default 0.79)
     i. Returns JSON: { success, predicted_deviation,
                        predicted_spend, r2_score }
 11. predict.php parses Python output, returns to PHP caller
 12. get-prediction.php returns to frontend
 13. BudgetContext stores in prediction state
 14. Analytics page displays predicted spend card

Online Learning (Month-End Update):
  - At month end, collect all users' completed month data
  - Run: php update_model_month_end.php
  - This calls update_model_partial_fit.py which:
    a. Loads existing model and scaler
    b. Appends new month's deviations to training set
    c. Calls model.partial_fit(new_data)
    d. Recalculates R² on combined dataset
    e. Saves updated model.pkl, scaler.pkl, model_metrics.json
  - R² will fluctuate ±2-3% normally (feature, not bug)
  - Large drops (>10%) indicate data quality issues

Progressive Prediction Fallback:
  Months | Method            | Confidence
  ───────┼───────────────────┼────────────
  0      | Budget baseline   | 20%
  1      | Single month      | 30%
  2      | Simple average    | 50%
  3      | Trend-adjusted    | 65%
  4+     | SGDRegressor ML   | 79%+

Trend-adjusted (3 months):
  average = (m1 + m2 + m3) / 3
  trend = m3 - m1
  prediction = average + 0.25 * trend
  (25% weight on recent trend direction)

9. BACKEND — FLASK SMS CLASSIFIER SERVICE (app.py)
================================================================================

Location: backend/app.py (417 lines)
Port: 5000
Framework: Flask + Flask-CORS

Algorithm: Multinomial Naive Bayes + TF-IDF Vectorizer
  - Implemented as sklearn Pipeline
  - Trained on 500,000 synthetic SMS messages
  - 8 categories: Food, Groceries, Transport, Health,
    Shopping, Entertainment, Subscriptions, Utilities
  - Test accuracy: 99.4%

Three-Layer Classification:
  Layer 0 — Hardcoded dictionary (instant, confidence=1.0):
    KNOWN_STORES dict with ~100 store→category mappings
    Examples: KFC→Food, Netflix→Subscriptions, Shoprite→Groceries,
              Engen→Transport, Clicks→Health, LEC→Utilities

  Layer 1 — Learned store memory (confidence=1.0):
    store_memory dict built from user confirmations
    Populated when a store reaches MIN_CONFIRMATIONS (5)
    Stored in memory (not persisted between restarts)
    Loaded from feedback_log.csv at startup

  Layer 2 — Naive Bayes ML classifier:
    TF-IDF vectorizes SMS text
    MultinomialNB predicts category
    If confidence >= CONFIDENCE_THRESHOLD (0.55): auto-assign
    If confidence < 0.55: return 'Other' + needs_manual_category=true

Bank Detection:
  detect_bank() scans SMS text for institution patterns:
  - FNB: "FNB:-)"
  - Standard Lesotho Bank: "has been reserved from acc"
  - M-Pesa: "transact id" / "M-Pesa"
  - Nedbank: "Nedbank confirms"
  - Ecocash: "ecocash"

Field Extraction:
  extract_fields() uses bank-specific regex patterns:
  - Amount: patterns like "M(amount) reserved for purchase"
  - Store name: extracted from transaction description
  - Balance: remaining balance after transaction
  - Transaction type: Purchase, Cash Withdrawal, Transfer

Cash Withdrawal Exclusion:
  - Detected by transaction_type or keyword matching
  - Keywords: "withdraw", "withdrawn", "cashout", "cash out",
              "atm", "pay 2wallet", "pay2wallet"
  - Withdrawals are assigned category='Other'
  - Withdrawals NEVER train the classifier
  - Reason: cash destination is unknown

Active Learning:
  POST /confirm_category
    Input: { sms, category, store, transaction_type? }
    Process:
    1. Checks if transaction is withdrawal → skips training
    2. Appends confirmation to feedback_log.csv
    3. Counts confirmations for this store+category combo
    4. If count >= MIN_CONFIRMATIONS (5):
       - Adds store to store_memory → auto-categorizes next time
    5. Retrains SMS model every RETRAIN_EVERY (5) confirmations
    Output: { success, trained, store, category,
              confirmations_count, memory_size }

Endpoints:
  POST /parse
    Input:  { sms: "SMS text" }
    Output: { bank, amount, store, balance, category,
              confidence, needs_manual_category, source,
              transaction_type, top_predictions[] }

  POST /parse_bulk
    Input:  { messages: ["sms1", "sms2", ...] } (max 500)
    Output: { results: [], count: N }

  POST /confirm_category
    Input:  { sms, category, store, transaction_type? }
    Output: { success, trained, reason?, store, category,
              confirmations_count, memory_size }

  GET /categories
    Output: { categories: [{ name, color }, ...] }
    Returns 9 categories with hex colors.

  GET /model_stats
    Output: { feedback_total, feedback_by_category,
              store_memory, store_memory_size,
              model_file, retrain_threshold }

  GET /health
    Output: { status: "ok", model_loaded,
              feedback_rows, store_memory_size }

Model Files:
  sms_classifier_v2.pkl — trained Pipeline (TF-IDF + NB)
  sms_dataset_v2.csv — 500,000 synthetic training messages
  feedback_log.csv — user confirmation log for active learning

Startup:
  1. load_or_train_sms_model() — loads .pkl or trains from CSV
  2. load_store_memory() — loads confirmed stores from feedback_log.csv
  3. Flask app starts on port 5000

17. FEATURE: SPENDING PREDICTION (SGDRegressor)
================================================================================

How it works:
  - Predicts end-of-month total spending
  - Based on user's historical budget-vs-actual patterns
  - Uses 4 months of past spending as features
  - Pre-trained SGDRegressor model predicts deviation from budget

Progressive fallback for new users:
  - 0 months: predicts = budget (assumes full budget spent)
  - 1 month: predicts = that month's actual
  - 2 months: predicts = average of both
  - 3 months: predicts = average + 25% trend weight
  - 4+ months: full ML prediction

Where displayed:
  - Analytics page: "Predicted Spend" card
  - Shows predicted amount, deviation from budget
  - Progress bar: predicted vs budget ratio
  - Confidence badge for non-ML methods
  - Method label shown (ml_model, trend_adjusted, etc.)

Model details:
  - Algorithm: SGDRegressor (squared_loss, SGD-based linear regression)
  - Features: 4 monthly deviations from budget
  - Target: next month's deviation from budget
  - Preprocessing: StandardScaler (zero mean, unit variance)
  - Training data: 500+ user records
  - R²: ~0.79-0.81 (loaded from model_metrics.json)
  - MAE: ~M224.56 (average prediction error)

Online learning:
  - Model updates monthly via partial_fit()
  - Script: backend/ml/update_model_month_end.php
  - Collects all users' completed month data
  - Incrementally updates model weights
  - Recalculates R² after each update
  - R² fluctuates ±2-3% normally

Limitations:
  - Requires 4 months for ML prediction
  - Cold users get statistical estimates only
  - Model assumes spending patterns are somewhat consistent

38. DATA FLOW DIAGRAMS
================================================================================

Expense Recording Flow:
  User → AddExpenseModal → BudgetContext.addExpense()
    → POST /api/add-expense.php → MySQL INSERT
    → BudgetContext.fetchDashboard() (refresh)
    → Dashboard re-renders with new data

Budget Setting Flow:
  User → SetBudgetModal → BudgetContext.updateBudget()
    → POST /api/update-budget.php → MySQL INSERT/UPDATE
    → BudgetContext.fetchDashboard() (refresh)
    → Dashboard + Analytics update

Prediction Flow:
  Analytics page mounts → useEffect triggers
    → BudgetContext.fetchPrediction(user_id)
    → POST /api/get-prediction.php → MySQL queries
    → (If 4+ months) → cURL to predict.php
    → predict.php → Python subprocess → run_prediction.py
    → Python loads budget_model.pkl + scaler.pkl
    → Returns predicted_spend → PHP → Frontend
    → Analytics page renders Predicted Spend card

SMS Auto-Categorization Flow:
  Bank SMS → Phone → SMS Forwarder App
    → POST webhook → /api/sms-ingest.php
    → Save raw SMS → MySQL (sms_raw_ingest)
    → cURL to Flask /parse (port 5000)
    → classify_sms() → 3-layer classification
    → Returns category, confidence, needs_manual
    → POST /api/auto-save-transaction.php
    → Save expense → MySQL (expenses)
    → Create notification → MySQL (notifications)
    → Dashboard auto-refreshes

Active Learning Flow:
  User sees "AI Needs Help" banner
    → Clicks transaction → CategoryPickerModal
    → Selects category → confirmSMSCategory()
    → POST Flask /confirm_category
    → Append to feedback_log.csv
    → If 5+ confirmations → add to store_memory
    → Next SMS from same store → auto-categorized (Layer 1)

39. SECURITY CONSIDERATIONS
================================================================================

Current Implementation:
  - Passwords hashed before storage (PHP password_hash)
  - ingest_secret: unique per user for webhook authentication
  - SMS hash (SHA-256) prevents duplicate processing
  - CORS headers set to Allow-Origin: * (development mode)
  - No CSRF tokens (localStorage-based auth)
  - No rate limiting on API endpoints
  - SQL parameterized queries (mysqli prepared statements)
  - Foreign key constraints maintain referential integrity

Known Gaps:
  - No HTTPS in local deployment
  - CORS Allow-Origin: * (should be restricted in production)
  - No API rate limiting
  - No input sanitization on all endpoints
  - localStorage tokens accessible via XSS
  - No 2FA support

40. KNOWN LIMITATIONS
================================================================================

Infrastructure:
  - Local XAMPP server only (not cloud-hosted)
  - Requires same WiFi network for mobile access
  - SMS Forwarder app is Android-only (no iOS support)
  - Flask service must be running separately

Prediction:
  - SGDRegressor requires 4 months for ML prediction
  - Statistical fallbacks are estimates, not ML
  - Model assumes somewhat consistent spending patterns
  - Seasonal variations affect accuracy

SMS Processing:
  - Supports only 4-5 banks (FNB, SLB, M-Pesa, Nedbank, Ecocash)
  - Requires physical SMS forwarding setup
  - Bank SMS format changes may break regex patterns
  - Store memory lost on Flask restart (in-memory only)

General:
  - No offline mode (PWA not implemented)
  - No multi-user/household budgeting
  - No recurring transaction detection
  - Duplicate component files exist (SetBudgetModal/Model)
  - Root-level legacy components not cleaned up
  - Some API endpoints have duplicate variants
